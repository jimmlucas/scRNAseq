# scRNAseq

Modular Nextflow/R pipeline for scRNA-seq, snRNA-seq and CITE-seq analysis.

This repository is the scientific execution engine. It owns reproducible
analysis, containers, checkpoints, validation, published artifacts and
Nextflow `-resume`.

BBUDY can supervise this pipeline from outside, but the pipeline does not
depend on BBUDY.

## Architecture

The project is designed around one pipeline and multiple ways to orchestrate
it:

```text
Human-reviewed policies
        ↓
External supervisor, optional
        ↓
Nextflow scientific engine
        ↓
R / Python scientific and control scripts
```

The separation is intentional:

```text
scRNAseq
  - runs Nextflow processes
  - manages Docker containers
  - validates inputs and policies
  - computes metrics and artifacts
  - applies only approved policies
  - preserves cache and resume behavior

External supervisor
  - interprets published artifacts
  - explains decisions to users
  - requests human review
  - prepares reviewed policy files
  - relaunches Nextflow with -resume
```

The pipeline should also remain usable without any supervisor:

```text
Nextflow + Docker + configs + approved policies
```

## Analysis Types

The same scientific engine is intended to support different single-cell
profiles. The shared pipeline backbone is reused, while modality-specific
capabilities are enabled by the analysis plan.

```text
scRNA-seq
  RNA QC
  RNA doublets
  RNA normalization
  PCA/UMAP
  integration when needed
  clustering, annotation and downstream analysis

snRNA-seq
  RNA QC with nuclear-aware thresholds
  ambient/intronic considerations
  doublets
  normalization
  PCA/UMAP
  integration, clustering and annotation

CITE-seq
  RNA QC
  AB QC
  SampleTag resolution when multiplexed
  RNA normalization
  AB CLR normalization
  integration by sample/run when needed
  WNN multimodal clustering
  optional BCR/TCR clonotype analysis
```

The analysis type is not a separate pipeline. It is a profile that activates
capabilities, expected modalities and policy gates.

## Causistics And Policies

The pipeline distinguishes between evidence, recommendations and decisions:

```text
metrics
  measurable values generated by modules

causistics
  structured evidence flags emitted from recurring situations

policy proposals
  technical options generated from metrics and causistics

reviewed policies
  human-approved decisions that validators can accept

application phases
  reproducible transformations using approved policies only
```

Examples of causistics:

```text
high_globin_content
repeated_sample_across_runs
sampletag_multiplet
undetermined_sampletag
ab_marker_removed
ab_low_feature_cells
ab_high_count_outliers
marker_based_doublet_signal
algorithmic_doublet_signal
integration_required
multimodal_wnn_applicable
small_cluster
annotation_uncertainty
pseudobulk_design_required
bcr_metadata_available
```

These are not free-form command-line flags. They are structured records with:

```text
causistic_id
severity
evidence
candidate_actions
policy_gate
emitted_by
emitted_at
```

The catalog is documented in:

```text
control/causistics_catalog.yaml
docs/analysis_patterns_from_legacy_rmds.md
```

An external supervisor can use these records to compare against previous
projects and explain options to scientists. Nextflow remains responsible for
producing evidence, validating reviewed policies and applying only approved
decisions.

## Standalone And Supervised Use

The same pipeline supports two execution styles.

In standalone mode, a user runs Nextflow directly with explicit inputs and
reviewed policy files:

```text
analysis plan
        ↓
Nextflow phase
        ↓
published artifacts
        ↓
human-reviewed policy file
        ↓
Nextflow validation/application phase with -resume
```

In supervised mode, an external system such as BBUDY can automate the control
loop around the same artifacts:

```text
run phase
        ↓
read metrics, warnings, policy proposals and causistics
        ↓
explain options using previous cases and scientific rules
        ↓
request human approval when required
        ↓
write reviewed policy file
        ↓
relaunch Nextflow with -resume
```

The difference is orchestration, not scientific behavior. The pipeline does
not know whether the next command was launched by a person, a script or an
external supervisor.

## Standalone QC Review

After `analysis_plan_qc_process`, the pipeline publishes a proposed QC
threshold policy plus impact diagnostics. The reviewer should not need to copy
YAML files manually. The standalone helper prepares the human-reviewed policy
artifact:

```bash
python3 scripts/control/review_qc_policy.py \
  --results-dir results_real_validation/K14897 \
  --decision approve \
  --reviewer jimmlucas
```

For a modified approval:

```bash
python3 scripts/control/review_qc_policy.py \
  --results-dir results_real_validation/K14897 \
  --decision modify-and-approve \
  --reviewer jimmlucas \
  --set percent.mito.max=15 \
  --set nFeature_RNA.min=200
```

The helper reads:

```text
control/qc_thresholds/qc_threshold_policy.yaml
control/qc_threshold_impact/qc_threshold_impact.summary.tsv
control/qc_threshold_impact/qc_threshold_impact_by_sample.csv
control/qc_threshold_impact/qc_threshold_impact_by_metric.csv
control/qc_threshold_impact/qc_lower_tail_summary.csv
```

and writes:

```text
qc_threshold_policy.reviewed.yaml
qc_threshold_policy.review.summary.tsv
qc_threshold_policy.review.session.txt
```

This is still non-destructive. It records a human decision, reviewer,
timestamp, reason, impact snapshot and optional threshold changes. It does not
validate the policy and does not filter cells. Nextflow still validates the
reviewed policy before application:

```bash
nextflow run main.nf \
  --mode qc_threshold_approval_phase \
  --analysis_plan configs/real_validation/K14897/analysis_plan.yaml \
  --approved_qc_threshold_policy configs/real_validation/K14897/review/qc_threshold_policy.reviewed.yaml \
  --project_id K14897 \
  --biological_run_id K14897 \
  --outdir results_real_validation/K14897 \
  -profile docker \
  -resume
```

## Phase Input Resolution

Published artifact paths are derived from `--outdir`. Users and external
supervisors should not have to remember every internal folder name. The phase
input resolver prints the canonical paths required by a downstream phase:

```bash
python3 scripts/control/resolve_phase_inputs.py \
  --outdir results_real_validation/K14897 \
  --phase qc_filter_policy_phase \
  --format shell \
  --require-existing
```

Example output:

```bash
INPUT_OBJECT=results_real_validation/K14897/01a_qc_metrics/seu_qc_metrics.rds
APPROVED_QC_THRESHOLD_POLICY=results_real_validation/K14897/control/qc_threshold_approval/approved_qc_threshold_policy.yaml
```

For doublet scoring:

```bash
python3 scripts/control/resolve_phase_inputs.py \
  --outdir results_real_validation/K14897 \
  --phase doublet_detection_scoring_phase \
  --project-id K14897 \
  --format shell \
  --require-existing
```

This helper does not run Nextflow and does not create scientific decisions. It
only resolves expected paths, reports whether they exist and fails early when a
phase is missing required upstream artifacts.

## Current Flow

The current plan-driven path reaches PCA-ready dimensionality artifacts:

```text
VALIDATE_ANALYSIS_PLAN
        ↓
RESOLVE_ANALYSIS_PLAN
        ↓
INPUT_DISCOVERY
        ↓
RESOLVE_LOAD_CONFIG
        ↓
LOAD_DATA
        ↓
QC_METRICS
        ↓
QC_THRESHOLD_RESOLUTION
        ↓
QC_THRESHOLD_IMPACT_SUMMARY
        ↓
VALIDATE_QC_THRESHOLD_APPROVAL
        ↓
QC_FILTER_POLICY
        ↓
SPLIT_SEURAT_BY_SAMPLE
        ↓
DOUBLET_DETECTION_SCORING
        ↓
DOUBLET_POLICY_RESOLUTION
        ↓
VALIDATE_DOUBLET_APPROVAL
        ↓
DOUBLET_FILTER
        ↓
POST_DOUBLET_QC_SUMMARY
        ↓
NORMALIZATION_POLICY_RESOLUTION
        ↓
VALIDATE_NORMALIZATION_APPROVAL
        ↓
NORMALIZATION
        ↓
DIMENSIONALITY
        ↓
PC_SELECTION_POLICY_RESOLUTION
        ↓
VALIDATE_PC_SELECTION_APPROVAL
        ↓
INTEGRATION_POLICY_RESOLUTION
```

`QC_THRESHOLD_IMPACT_SUMMARY` is non-destructive. It simulates the
consequence of a proposed QC policy before approval, publishing per-sample,
per-metric and overlap summaries so a reviewer can judge the biological impact
before `QC_FILTER_POLICY` removes any cells. It also publishes lower-tail
diagnostics for low-complexity signals such as very low `nFeature_RNA`,
`nCount_RNA` and `log10GenesPerUMI`, allowing reviewers to spot weak lower
tails without converting those probes into automatic filters.

`SPLIT_SEURAT_BY_SAMPLE` is a non-destructive checkpoint between QC filtering
and doublet scoring. Think of it as placing each biological sample on its own
bench before a technician starts sample-specific work. The original
QC-filtered object remains unchanged, while the phase publishes one Seurat RDS
per sample plus `01f_split_by_sample_manifest.tsv`. That manifest is the
contract future per-sample modules can consume, allowing doublet detection to
be parallelized and resumed per sample without making BBUDY or the user depend
on hand-written paths.

`DOUBLET_DETECTION_SCORING` is also non-destructive. It annotates cells with
DoubletFinder scores and proposed classes but does not remove cells. The
legacy mode still accepts a single QC-filtered object. The by-sample mode
accepts `sample_manifest`, `sample_objects` and `doublet_config`, launches one
scoring task per sample, then merges the results back into the canonical
`01g_doublet_detection_scoring` outputs. Downstream phases therefore still
consume the same `seu_doublet_scored.rds`, summary, by-sample, cell-score,
pK-sweep and performance artifacts.

Both doublet scoring modes publish `01g_doublet_detection_performance.csv`, a
per-sample runtime profile covering normalization, HVG selection, scaling, PCA,
pK sweep and final DoubletFinder scoring. This artifact is operational
evidence for comparing local Docker, VM and HPC performance; it is not a
scientific decision gate. The DoubletFinder pK sweep can use
`doublet.sweep_cores`, defaulting to `1`, so deployments can choose between
per-sample parallelism and internal sweep parallelism without changing the
scientific policy.

The next scientific block is integration approval validation.

## Policy Pattern

Scientific decisions are separated from scientific execution:

```text
calculate metrics
        ↓
propose policy
        ↓
human review
        ↓
validate reviewed policy
        ↓
apply approved policy
        ↓
publish audit artifacts
```

This pattern is already used for:

```text
QC thresholds
Doublet filtering
Normalization strategy
PC selection
Integration strategy
```

Application phases must not recalculate decision proposals. They consume only
validated policy files.

Technical phases without a new scientific decision, such as scaling variable
features and PCA, stay as deterministic application phases. They publish
evidence for later decisions but do not introduce unnecessary approval gates.

PC selection is deliberately separated from PCA calculation because the chosen
number of PCs affects neighbors, UMAP, clustering and integration.

## Execution Modes

The canonical interface is phase-level execution. This keeps debugging,
checkpoint recovery and external orchestration simple.


## Development Rule

Keep the scientific engine neutral:

```text
Do not put supervisor-specific logic inside Nextflow modules.
Expose artifacts, policies and modes.
Let external tools decide what to run next.
```
